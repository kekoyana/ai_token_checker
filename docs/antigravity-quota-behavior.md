# Antigravity (agy) のクォータ挙動

`agy` が `Individual quota reached` で止まった件の調査記録。
`usage_check.py` の agy 行がなぜ枯渇を映さなかったか、リセット時刻をどう読むべきかを含む。

## 症状

```
⚠ Individual quota reached. Please upgrade your subscription to increase your limits.
  Resets in 62h17m26s.
```

- リセットまで62時間もあるため「まだ余裕がある」と読めてしまう。
- 同時刻の `usage_check.py` には **枯渇した枠が1行も出ていなかった**。
- その1時間20分前（21:00）には該当枠が `残り6.2% / 計測初期` と表示されており、
  「計測初期」を余裕があるサインと誤読した。

## 原因（調査で確定した挙動）

### 1. モデルグループごとにリフレッシュ周期が違う

Antigravity IDE の Models 画面の表示。

| グループ | 周期 | 画面表示 |
|---|---|---|
| Claude Sonnet/Opus 4.6, GPT-OSS 120B | 5時間 | `Refreshes in 4 hours, 56 minutes` |
| Gemini 系 8モデル | 約3日 | `Refreshes in 2 days, 13 hours` |

画面下部に `Model quota refreshes periodically based on your plan` とある通り、
**枠ごとに周期が決まっている**。5時間サイクルの Claude 枠と同じ感覚で Gemini 枠を見ると外す。

### 2. `resetTime` の意味が枯渇の前後で変わる

**枯渇した枠は実際の期限を返し、生きている枠は目安を返す。**

- 生きている枠（Claude）: 取得のたびに前へずれる。実際のリセット期限ではない。
- 枯渇した枠（Gemini）: 秒まで完全固定。これが本物の期限。

したがって **`Resets in ...` の長さは残量とは無関係**。長いほど余裕があるのではなく、
枯渇後に初めて現れる「その間まったく使えない期間」を意味する。

### 3. API は Gemini 系の残量を返さない

`antigravity-usage quota --json` のモデルエントリのフィールドは以下7種のみ。

```
isAutocompleteOnly, isExhausted, label, modelId,
remainingPercentage, resetTime, timeUntilResetMs
```

- Gemini 系は `remainingPercentage` キー自体が**存在しない**（Claude 系にはある）。
- 同一モデルの重複エントリはなく、**5時間枠と72時間枠を別々に返す構造にはなっていない**。
- `isExhausted` は枯渇中でも `false` のことがあり、枯渇判定には使えない。

### 4. Gemini アプリの枠とは完全に別

同一アカウント `arihh0615@gmail.com` の同時刻の状態。

| 参照先 | 状態 |
|---|---|
| Gemini のページ（PRO） | **0% 使用中**（5時間枠・週次枠とも無傷） |
| Antigravity (agy) | **Gemini 8モデルが枯渇** |

**Gemini のページを見ても agy の残量は分からない。**

## 実測ログ（2026-08-30）

### resetTime の推移（同一セッション内で6回取得）

| 取得時刻(JST) | Claudeグループ | Geminiグループ |
|---|---|---|
| 22:28:41 | 08/31 03:28:41 | 09/02 12:40:23 |
| 22:52 | 08/31 03:52 | 09/02 12:40:23 |
| 23:01 | 08/31 04:01 | 09/02 12:40:23 |
| 23:09:19 | 08/31 04:07:56 | 09/02 12:40:23 |
| 23:10:18（0.3秒差の連続取得） | 08/31 04:07:56 | 09/02 12:40:23 |

Gemini は42分間まったく動かない（秒まで一致）。Claude は取得のたびに前へずれる。
短時間の連打では Claude も動かないので、サーバー側の丸めかキャッシュが入っている。

### 枯渇までの経緯

`agy -p`（print mode）を短間隔で連続実行していた。

```
22:20:04  429なし  ← 成功（消費中）
22:20:33  429なし
22:20:56  429なし
22:21:23  429なし
22:21:48  429なし
────────── 22:22:04 枯渇 ──────────
22:22:23  429×5
22:22:29  429×5
   … 22:23:26 まで計8本、すべて429
```

- 前半5本が約25〜30秒間隔で消費し切り、**22:22:04 に枯渇**。
- 枯渇後も**7〜8秒間隔に加速して8本を起動**。各セッションが内部で2回リトライするため、
  無駄打ちだけで40件以上の429を記録した。

### 過去のリセット時刻（参考）

| 記録 | 間隔 |
|---|---|
| 08/29 15:35 → 08/30 02:39 | 11.1時間 |
| 08/30 02:39 → 08/30 17:30 | 14.8時間 |
| 08/30 17:30 → 09/02 12:40 | 67.2時間 |

間隔が固定でないのは、枯渇前の値が「目安」だったため（上記2)。
最後だけ長いのは、枯渇して実際の期限に切り替わったから。

## 未確定

**Gemini 枠が5時間枠と72時間枠の2階層を持つかは未検証。**

- API にも IDE にも1モデル1リセット時刻しか出ておらず、2階層の証拠は取れない。
- ただし「ない証拠」にもならない。Claude Code も Gemini アプリも枠は2階層であり、
  API が逼迫している方だけを返している可能性が残る。
- **検証方法**: Claude グループがリセットされる前後（今回なら 08/31 04:08 頃）に
  Gemini が部分回復するかを見る。回復すれば2階層、しなければ72時間枠のみ。

## 対処

1. **429 が出たら即中断する。** リトライは枠を回復させないうえ、ログを汚す。
2. **連続実行にレート制限を入れる。** 25秒間隔で12連発は3日周期の枠には速すぎる。
3. **AI Credit Overages**（IDE の Models 画面）を ON にすると、枠が尽きた後は
   AI クレジットで継続できる。クォータが優先消費されるため、通常時の消費は変わらない。
4. 残量の確認先は用途で使い分ける。

| 確認先 | 分かること |
|---|---|
| **Antigravity IDE の Models 画面** | 残量バー・周期・警告マーク。**最も情報が多い** |
| `antigravity-usage quota --json` | リセット時刻。Gemini の残量は取れない |
| Gemini のページ | agy とは別枠。**参照しても無意味** |

## `usage_check.py` 側の対応（コミット cc9da45）

- `remainingPercentage` を返さないモデルを一覧から落とさない。
  従来は**枯渇した枠だけが表から消える**という最悪の挙動だった。
- `window_minutes=300`（5時間）を62時間先のリセットに適用しない。
  `elapsed_fraction` が -11.7 になり、残り6.2%の枠に `計測初期` が付いていた。
- 残量が少ない事実をペース推定より優先（`枯渇寸前` / `残りわずか`）。
- `計測初期` ラベルを廃止。必要なときに叩く CLI で判定を伏せる意味がない。

残る限界: API が Gemini の残量を返さない以上、その列は `不明` にしかならない。
これは実装ではなくデータ源の制約。

## 教訓

`Resets in ...` の残り時間は残量ではない。**長いほど深刻**である。
枯渇して初めて実際の期限が現れるため、「まだ62時間ある」は「62時間使えない」と読む。
