# Claude 使用量取得が HTTP 429 になる件

`usage_check.py` の Claude 行が `APIエラー HTTP 429` になる場合の調査記録と対処。

## 症状

```
claude    ERROR    -    -    -    -    -    APIエラー HTTP 429
```

`claude_usage()` が叩く `https://api.anthropic.com/api/oauth/usage`（`usage_check.py` 内）が
`429 Too Many Requests` を返している状態。

```
HTTP/2 429
retry-after: 3529
{ "error": { "type": "rate_limit_error", "message": "Rate limited. Please try again later." } }
```

## 原因（調査で確定した挙動）

- **認証切れでもクォータ枯渇でもない。** トークンは有効（無効なら 401）。エラー種別は `rate_limit_error`。
- レート枠は **スクリプト単位ではなくアカウント（OAuthトークン）単位**。
- この使用量エンドポイントは **Claude Code 本体（CLI）も定期的に叩く**ため、`usage_check.py` を本日初回実行しても、
  同じトークンを使う他クライアントのアクセスで既に枠が埋まっていれば 429 になる。
- **枠はスライディング型**。`retry-after` の指すリセット時刻は、アクセスするたびに「そこから約1時間先」へ更新される。
  - 実測: 21:11 に実行 → その後の観測で reset ≈ 22:12（＝ 21:11 + 約61分）。
  - このため **触るほど解けにくくなる**。デバッグ目的の連続アクセスも枠を後ろへ押す。

### 実測ログ（2026-07-17）

| 観測時刻(JST) | retry-after | 指すリセット時刻 |
|---|---|---|
| 19:49 | 3449 | 約20:47 |
| 21:13 | 3529 | 約22:12 |
| 21:14〜21:15（60秒で3連続） | 3488→3458→3428 | すべて 22:12 で一致 |

短時間の連打では reset は動かないが、時間を空けたアクセスで reset が後ろへ移動する（スライディング枠）。

## 対処

1. **これ以上叩かない。** `usage_check.py` の再実行を含め、約1時間は完全に放置する。
2. 同じトークンを使う **他の Claude Code セッションも止める**（動いていると枠を更新し続ける）。
3. 放置後に **1回だけ**実行する。
4. スクリプト側の改善案: 429 時に `retry-after` を読んで「約N分後に再試行」と表示し、**自動リトライはしない**
   （自動リトライは枠を押し続け逆効果）。

## 教訓

429 の切り分けで同じエンドポイントを繰り返し叩くと、スライディング枠を自分で延長してしまう。
このエンドポイントは「観測するほど状態が悪化する」ため、まず放置を優先する。
